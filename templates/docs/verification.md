# 통합 검증

수용 기준별로 기대값과 관찰값을 비교한다. 테스트 코드를 작성했어도 실행 전 판정은 미검증이다.

- 현재 PRD·데이터 계약 리비전
- 검증 context와 실제 실행 결과·evidence 경로
- PRD·계약·데이터·코드·테스트 해시의 현재 일치 여부
- 필수 AC 목록·검증 범위와 마지막 최신성 확인 결과

| AC ID / 시나리오 ID / 코드 위치 | 검증 종류·환경·입력 | 실행 명령 또는 수동 절차 | 기대값 | 실제 관찰값·근거 위치 | PASS / FAIL / 미검증 |
|---|---|---|---|---|---|

## BE 시나리오

BE가 있는 과제는 담당 유스케이스에서 정상·실패·경계 시나리오를 약 30건 도출한다. 과제의 기존 테스트 관리표가 있으면 해당 위치를 참조한다.

| 시나리오 ID / 관련 AC | 우선순위 | 사전 상태와 입력 | 실행 행동 | 기대 응답과 저장 상태 | 단위 / API 통합 | 테스트 위치 |
|---|---|---|---|---|---|---|

- 실제 구현한 기능에 해당하는 범주를 선택한다. 개수를 조정하면 이유를 적는다.
- 기대값은 테스트 실행 전에 계약이나 독립 계산으로 정한다. 실제 실행·판정은 위 검증표에서 관리한다.
- 전체 시나리오 수, PASS/FAIL/미검증 건수, 테스트가 연결되지 않은 필수 AC와 업무 분기를 확인한다. 코드 커버리지를 측정했다면 범위와 결과를 따로 남긴다.

## 공통 검증 원칙

- 핵심 흐름과 결과를 뒤집을 만한 반례 한 건을 우선 확인한다.
- KPI는 [기준선](data-report.md)과 같은 입력·산식·분모로 비교한다. 적용하지 않는 항목은 사유를 남긴다.
- 수동 UI 관찰은 확인 주체와 실제 본 결과를 기록한다. 모의 응답, 실제 API, 실제 화면 증거를 구분한다.
- 실패한 행은 재현 조건과 수정 후 재실행 결과를 연결한다. 필수 AC가 실패·미검증이면 전체 통과를 선언하지 않는다.
