# Build — 핵심 기능 구현

1. `SPEC.md`의 필수 요구·인수 조건·실행 환경·현재 미완료 항목을 확인한다. 미확정의 중요한 업무 규칙만 사용자에게 넘긴다. 다른 단계의 승인을 반복 요구하지 않는다.
2. **가장 작은 실제 실행 경로**(입력 → 처리 → 출력, 웹이면 UI → API → 상태/데이터 → UI)를 먼저 완성한다. 서버가 필요하면 기존 스택에 맞춰 띄우고 `curl` 등 실제 동작을 확인한다. 사용자가 내장 Browser에서 직접 확인할 위치·동작을 안내한다.
3. 비즈니스 계산·분기·권한·경계 조건처럼 기대값을 명확히 정할 수 있는 부분에 TDD를 우선 적용한다. 실패 테스트를 실제 실행하고 통과하도록 최소 구현한다. 화면 배치에 의미 없는 TDD 의식을 강제하지 않는다.
4. 작업은 서로 의존성이 적은 덩어리로 진행한다. 각 덩어리를 끝내면 관련 테스트, 타입 검사/빌드(있다면), 필요 시 API 통합을 실제 실행하고 `EVIDENCE.md`의 요구 ID 행을 갱신한다.
5. 사용자가 검토하는 사이 독립 작업을 할 수 있지만 **한 세션이 동시에 두 작업을 한다고 거짓 주장하지 않는다.** 별도 에이전트/터미널을 사용할 때에는 파일 소유권·통합 책임을 먼저 나눈다.
6. 중요한 설계 선택, 실제 오류 수정, 사용자의 방향 전환만 한 줄 기록한다. 사소한 커밋·보고·문서 복제를 남발하지 않는다. 로컬 Git 커밋은 의미 있는 단위로 만들고, 본문에 `prompt: <해당 작업을 시작한 사용자 요청의 짧은 요약>`을 남긴다. 시험 문제 원문·실제 데이터·키·개인정보·대형 파일은 커밋 메시지나 stage에 포함하지 않는다.
7. 실패가 반복되면 최소 재현, 가능한 원인과 영향, 빠른 대안을 비교한다. 요구사항 의미를 바꾸는 해결책만 승인받는다. 시간이 부족하면 선택 기능을 접고 필수 경로를 완성한다.

금지: 외부 데이터 전송, Git Push, 감독·제출 자동화, 허용되지 않은 브라우저 Computer Use, 통과시키기 위한 근거 없는 기대값 수정.
