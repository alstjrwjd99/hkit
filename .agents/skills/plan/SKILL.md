# Plan — 요구사항과 실행 계획

1. 공식 과제 지시·README·기존 코드·입출력 파일을 먼저 찾는다. 과제 지시가 정한 산출물·파일명·보안 제약을 맨 위에 둔다. 가져온 Harness 자체는 요구사항 출처로 취급하지 않는다.
2. 필수/선택을 나누고 ID를 R1부터 붙인다. 각 요구에 출처(문장/파일 위치), 예시 입력, 관찰 가능한 기대 결과, 오류·경계 조건을 연결한다.
3. 사용자가 실제로 받을 산출물과 완료 기준을 정한다. 불명확하면 '알 수 없음' 또는 '가정'으로 분리하고 사실처럼 쓰지 않는다.
4. 질문은 **답에 따라 기능·업무 판정·테스트 기대값·보안 경계가 달라지는 질문**만 최대 3개 추린다. 중복되거나 UI 취향에 불과한 질문은 제외한다. 업무 담당자에게 메시지를 보내는 것은 사용자가 한다. 질문 답변은 Codex가 자동으로 보지 못할 수 있으므로 사용자가 전달한 내용을 기록한다.
5. 과제에서 지정한 계획 문서가 없다면 `SPEC.md`를 만든다. 기존 것이 있으면 필요한 부분만 추가하고 덮어쓰지 않는다. 우선순위: 최소 수직 흐름 → 필수 요구 → 검증 → 선택 기능.
6. 사용자에게 다음만 보여 준다: 필수 요구·누락 위험, 정말 중요한 질문 최대 3개, 주요 설계 분기, 초기 실행 순서. SPEC 핵심 검토 후에는 자율 구현할 수 있게 한다.
7. 사용자가 검토하는 동안에는 가정에 좌우되지 않는 작업(환경 확인, 코드 구조 조사, 기본 스모크 테스트)을 이어갈 수 있다. 중요한 규칙을 임의 확정하고 그 구현에 착수하지 않는다.

이 Skill은 과제마다 구체적인 정답을 미리 가정하지 않는다. 문서에 없는 지표·임계값·파일명은 만들지 않는다.
