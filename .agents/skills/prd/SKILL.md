# PRD 작성

1. 과제 원문과 기존 SPEC에서 요구 ID(R1 등), 출처, 필수 범위와 금지 조건을 읽는다. 주 사용자가 어떤 입력으로 무엇을 결정하고 어떤 결과를 받아야 하는지 한 문장으로 쓴다.
2. `docs/prd.md`에 필수 사용자 흐름과 제외 범위를 적는다. 수용 기준마다 R1-AC1처럼 고정 ID를 붙이고, 시작 조건·사용자 행동·관찰할 기대값·검증 방법을 정한다. 오류나 경계에서 결과가 달라지면 별도 기준을 둔다. SPEC의 요구 행에서 이 기준을 가리킨다.
3. 1차 KPI의 산식·단위·평가 대상·개선 방향·목표 출처를 적는다. 데이터가 있으면 EDA가 측정한 기준선과 제약을 연결한다. 목표가 주어지지 않았다면 측정치와 제안 목표를 구별한다. 데이터로 판정할 수 없는 목표 간 우선순위는 사람에게 맡긴다.
4. 화면과 서버가 나뉘면 오케스트레이터가 `docs/api-contract.md`에 호출 예, 요청·응답 타입, 누락/null 및 오류 처리, 해당 AC와 구현 소유 경로를 기록한다. 기존 OpenAPI/공유 타입이 있으면 해당 정의를 참조한다. FE·BE가 같은 예로 각각 구현·검증할 수 있을 때 계약을 확정한다.

인계할 때 이번에 구현할 AC, 데이터를 더 확인할 부분, 사람의 결정이 필요한 쟁점을 구분한다. 과제에서 지정했거나 이미 운영 중인 동등한 문서가 있으면 그 자리에서 갱신한다.

## EDA와 양방향으로 합의

- **분석 요청.** PRD에 P1 같은 리비전과 H1 같은 가설 ID를 두고, 관련 R/AC·검증할 주장·KPI 산식/단위·평가 대상/기간·입력 경로·비교할 기준·결과로 결정할 일을 정한다. 관측 가능한 데이터가 있는지와 별개로 품질·실현 가능성을 먼저 조사할 수 있다.
- **반환 검토.** EDA가 제시한 입력 식별값·조사 범위·재실행 명령·관찰 결과·한계를 확인한다. 영향받는 R/AC별로 제안을 수용·수정·보류하고 이유와 연결할 BE 시나리오를 기록한다. 검증할 수 없는 가설은 미검증으로 두고 필요한 입력이나 대안을 정한다.
- **요구 수정.** 근거로 구체화할 수 있는 타입·누락 처리 등은 기존 요구와 맞춰 갱신한다. 문제 정의·주 KPI·우선순위·범위가 바뀌는 결정은 부모가 `$explain`으로 전달한다. 요청에는 관련 R/AC, 대안별 관찰값과 근거 경로, 사용자 영향, 권고와 필요한 결정 하나를 담는다. 실제 답변을 결정 로그에 남긴 뒤 관련 PRD·계약을 갱신한다. 제안 단계에서 새 목표를 확정된 AC로 바꾸지 않는다.
- **재분석.** PRD를 P2로 갱신하면 바뀐 가설·산식·분모·입력을 지정해 해당 결과만 다시 계산한다. 동일 입력·분석 조건의 원시 관찰값은 근거로 참조하고, 현재 검증의 판정은 현재 PRD·계약·데이터·코드·테스트에 연결해 새로 기록한다. 새로운 증거가 없거나 입력·자원이 부족하면 남은 불확실성과 다음 결정을 명시한다.
- **구현 인계.** 필수 AC의 데이터 실현 가능성이 확인되고 필요한 KPI가 재현되면 API·데이터 계약 리비전을 맞춰 BE에 전달한다. 미해결 분석이 있는 기능은 영향 범위를 보류하고 독립적으로 구현 가능한 요구는 진행한다. 확정 뒤 분석 결과가 바뀌면 영향받는 계약·테스트를 함께 갱신한다.
