# Check — 검증 및 증거 확인

1. SPEC의 필수 요구 R1…Rn, 연결된 PRD의 AC, 과제 지정 산출물을 읽는다. 메인 세션이 FE·BE 결과를 실제 계약·통합 환경에서 다시 확인한다.
2. 요구별로 `실제 코드 위치 → 검증 방법 → 명령/절차 → 관찰 결과 → 판정`을 만든다. 기존 테스트·빌드·타입 검사·API 호출을 실행하고 결과를 기록한다. 테스트가 없으면 핵심 위험을 검증하는 최소 사례를 제안하거나 추가한다.
   BE가 있으면 시나리오 표의 관련 AC, 테스트 위치와 실제 실행을 대조한다. 정상·경계·실패 중 빠진 업무 분기, 중복 요청과 실패 시 저장 상태 등 해당하는 조건을 확인하고, 전체 건수와 PASS/FAIL/미검증을 집계한다.
3. 검증 계층을 정확히 구분한다: (a) 정적 검사 (b) 단위 테스트 (c) API·로컬 통합 (d) 실제 사용자 흐름 수동 확인 (e) 미실행. `curl` 200은 UI E2E 통과를 증명하지 않는다.
4. UI 화면 검사는 Cofa 내장 Browser를 사용자가 직접 수행하도록 포트·경로·동작 2~3개를 안내한다. **AI 브라우저 자동 조작/Computer Use를 실행하지 않는다.** 과제 규정이 허용한다고 명시한 별도의 자동 테스트 실행만 고려한다.
   화면을 바꿨다면 좁은 폭과 기본 폭에서 핵심 정보·다음 행동이 보이는지, 빈 영역과 잘린 내용이 없는지 확인한다. 배경으로 정보의 위계가 드러나는지, 주 버튼이 식별되는지, 변경한 컴포넌트의 기본·상호작용 상태가 두 색 이내인지 대조한다. 수동으로만 확인할 수 있는 결과는 관찰을 전달받은 뒤 기록한다.
5. 핵심 정상 사례 1개, 실패/경계 사례 1개 이상을 우선 검증한다. 잘못된 입력, 누락 값, 중복, 인증/권한, 데이터 무결성, 기초 성능 등은 과제에 직접 관련된 것만 고른다. 수치·판정의 핵심 기대값은 구현 코드 외부의 원자료·독립 계산과 대조한다.
6. 코드 수정 전 실패를 재현하고 같은 조건으로 재실행한다. 테스트 기대값을 결과에 맞추거나 mock만 통과시키고 실제 통합 검증이라고 적지 않는다.
7. KPI가 있으면 EDA 기준선과 같은 표본·산식·분모로 재계산해 PRD 목표와 대조한다. `docs/verification.md`(또는 기존 검증표)에 AC별 기대값·실제 출력·명령과 PASS/FAIL/미검증을 기록한다. 필수 AC가 빠졌거나 실패·미검증이면 전체 통과 판정을 보류하고 영향과 다음 확인을 보고한다. 읽기 전용 리뷰는 결과만 전달한다.
   EDA가 있으면 보고서의 분석 요청·입력·조사 범위가 현재 PRD와 맞는지 확인한다. 핵심 명령을 재실행하고, 요구 변경의 처리 결과와 데이터 계약의 확정 제약이 BE 코드·시나리오에 연결됐는지 대조한다. 표본 프로파일·재현하지 못한 기준선·확정 전 제약을 완료로 표시하지 않는다.
8. 검증을 시작하기 전에 현재 PRD·데이터 계약·입력 데이터·관련 코드·테스트 파일과 필수 AC를 [검증 기록 규격](references/evidence.md)의 context에 선언하고 해시를 캡처한다. 실제 실행 결과를 기록한 뒤 완료 직전에 `scripts/verify_evidence.py`로 현재 입력과 대조한다. 변경·실패·미검증·필수 AC 누락이면 완료를 보류하고 영향받는 검증을 다시 실행한다. 이전 기록은 해당 리비전의 이력으로 보존한다.
