# API와 업무 규칙 구현

기존 서버·저장 방식·테스트 도구를 따르고 배정된 BE 및 테스트 경로에서 작업한다. 계약이 모호하면 필요한 변경과 소비자 영향을 부모에게 전달한다.

## 유스케이스에서 시나리오 도출

1. PRD의 담당 AC와 API 계약을 읽고 사용자 행동, 시작 상태, 입력, 기대 응답과 저장 상태를 연결한다. EDA가 있으면 [데이터 계약 규격](../eda/references/data-contract.md)에 따라 현재 PRD와 연결된 데이터 계약을 읽는다. 확정 제약을 기존 입력 검증에 연결하고 제약 ID별 정상·위반·경계 테스트를 만든다. 관찰값은 테스트 데이터 후보와 분석 근거로 사용한다. 지원하지 않는 규칙이나 리비전 불일치는 부모에게 전달한다.
2. 유스케이스별 정상·실패·경계 시나리오를 합쳐 약 30건을 초안으로 만든다. 아래 범주에서 실제 기능에 해당하는 조건을 골라 서로 다른 업무 분기와 상태 전이를 덮는다. 기능이 단순하거나 복잡하면 개수를 조정하고 이유를 적는다.

| 범주 | 선택할 조건 |
|---|---|
| 정상 사용자 흐름 | 생성·조회·변경 등 실제 제공 기능, 선택 입력 유무, 상태 전이 |
| 입력과 경계 | 필수값 누락, 타입·형식 오류, 빈 값, 최소·최대와 그 직전·직후, EDA에서 발견한 품질 문제 |
| 접근과 대상 상태 | 인증 만료·역할·소유권, 없는 대상, 이미 완료된 대상 등 구현된 규칙 |
| 조회와 계산 | 빈 결과, 필터·정렬·페이지 경계, 단위·반올림·시간 경계 등 해당 기능 |
| 저장과 복구 | 중복 요청, 재시도, 동시 변경, 저장·외부 호출 실패 시 상태 보존과 복구 |

3. 각 시나리오에 B01 같은 ID, 관련 AC, 우선순위, 사전 상태·입력, 실행 행동, 기대 응답·저장 결과, 검증 계층을 정한다. 같은 분기를 반복하는 경우는 매개변수화한다. 기대값은 계약·원자료·독립 계산으로 정한다. 출처가 없는 업무 규칙은 쟁점으로 전달한다.
4. 시나리오 표는 `docs/verification.md`의 BE 시나리오 절 또는 기존 테스트 관리 문서에 둔다. 하위 에이전트는 표 초안을 부모에게 전달하고 배정된 테스트 파일에 시나리오 ID를 연결한다. 공통 문서는 부모가 갱신한다.

## 테스트와 구현

- 계산·분기·상태 전이는 단위 테스트로 실패를 먼저 확인하고 최소 구현으로 통과시킨다. API 통합 테스트는 실제 앱 진입점에서 요청 검증, 상태 코드와 본문, 필요한 저장 상태 변화를 함께 단언한다.
- 저장을 사용하는 핵심 흐름은 격리된 테스트 저장소까지 연결한다. 쓰기 도중 실패했을 때 부분 저장이 남는지, 같은 요청의 재전송이나 동시 요청이 업무상 불변 조건을 깨는지 해당 기능의 계약에 따라 확인한다.
- 테스트마다 데이터를 준비·정리해 실행 순서에 의존하지 않게 한다. 시간·난수·외부 응답을 제어했다면 조건을 밝히고 실제 연동을 확인한 범위를 구별한다. 기존 테스트를 재사용하고 같은 조건에서 수정 전 실패와 수정 후 통과를 확인한다.
- 정상 핵심 흐름과 필수 AC, 결과를 뒤집는 경계·실패를 우선 실행한다. 코드 커버리지를 측정할 수 있으면 변경한 업무 분기의 누락을 확인한다. 시나리오 수와 실행 통과율, 코드 커버리지는 각각 기록한다.

## 검증 인계

담당 AC별 테스트 위치와 B ID, 실행 명령, 기대값·실제 관찰, 테스트 저장소·mock 사용 범위를 부모에게 보낸다. PASS/FAIL/미검증 건수와 아직 덮지 못한 필수 AC·분기를 명시하고, 부모가 전체 수용 기준의 누락을 대조하도록 한다.
