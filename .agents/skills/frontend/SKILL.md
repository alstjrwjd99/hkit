# 사용자 흐름 구현

기존 화면·테스트 구조에서 배정된 경로만 편집한다. 공유 타입이나 계약이 맞지 않으면 오케스트레이터에게 필요한 변경과 영향을 보낸다.

## 화면을 만드는 순서

1. **표시할 정보 선택.** PRD의 담당 AC마다 사용자가 내려야 할 판단과 다음 행동을 적는다. 그 판단에 필요한 값·단위·상태를 API 필드와 짝짓고, 항상 보여 줄 핵심 정보와 필요할 때 펼칠 세부 정보를 나눈다.
2. **ASCII 구조 시안 비교.** 코드를 쓰기 전에 화면 구조 시안 2~3개를 ASCII 박스로 그려 사람에게 보여 주고, 고른 시안으로 구현한다. 각 시안은 1단계의 핵심 판단에서 출발해 무엇을 나란히 놓고 무엇을 순서대로 놓을지가 서로 달라야 한다. 시안마다 실제 값과 라벨을 넣고, 아래에 장단점을 한 줄씩 붙인다. KPI 카드 줄 + 패널 격자 같은 대시보드 틀을 기본값으로 쓰지 않는다. 핵심 판단이 비교라면 비교 대상을 나란히, 순서라면 흐름대로 놓는다. 시안은 `$plan`의 핵심 검토에 함께 올려 승인을 한 번으로 끝낸다. 서브에이전트로 실행 중이면 시안을 부모에게 돌려주고 선택을 받은 뒤 구현한다. 고른 시안을 바꿔야 할 정도로 구조가 틀어지면 같은 방식으로 다시 보여 준다.

   ```text
   +----------------------------+----------------------------+
   | P1 현재 규칙 (행마다 집계) | P2 제안 (관측 ID 고유)     |
   |  7.2분  분자 360 / 분모 50 |  8분  분자 240 / 분모 30   |
   |  O1 A 11-01  10  12        |  O1 A 11-01  10  12        |
   |  O2 A 11-02  20   6 (중복) |  O2 A 11-02  20   6        |
   +----------------------------+----------------------------+
   |  차이 +0.8분          [보류] [거절] [ P2 적용 ]          |
   +---------------------------------------------------------+
   장점: 판단할 두 정책이 한눈에 비교된다 / 단점: 표가 두 번 나온다
   ```
3. **무채색 레이아웃 배치.** 기본 글자와 컨트롤만으로 실제 길이의 데이터를 배치한다. 핵심 값과 해당 행동을 가까이 두고, 빈 열·고정 높이·겹친 카드 패딩을 없애 불필요한 여백을 최소화한다. 좁은 폭에서는 읽는 순서대로 쌓고, 항목을 구별할 간격과 클릭 영역을 확보한다. 이 단계에서 내용과 배치를 먼저 확인한다. 공백은 아래 기준으로 판정한다.
   - 카드·패널 안에서 내용이 없는 높이나 너비가 그 요소의 1/4을 넘으면 패딩·고정 높이·늘어나는 열을 줄인다.
   - 짧은 값으로 된 표를 폭 100%로 늘려 열 사이를 벌리지 않는다. 짧은 열은 내용 폭에 맞추고 남는 폭은 마지막 열이나 설명 열이 받는다.
   - 한 카드의 라벨과 핵심 값을 양 끝으로 밀어 두지 않는다(`space-between`, `auto` 열). 값과 그 설명은 붙여 둔다.
   - 화면의 1/4 이상이 비면 콘텐츠를 늘리거나, 영역 높이를 줄이거나, 정렬로 처리하는 순서로 고친다. 글자를 키워 공백을 메우거나 글자를 줄여 밀도를 만들지 않는다.
4. **중요도에 따라 배경 구분.** 핵심 결과 묶음에는 강조용 중립 배경, 일반 본문에는 기본 배경, 보조 설명에는 옅은 배경을 쓴다. 같은 중요도의 영역은 같은 배경을 공유한다. 제목과 배치만으로도 순서를 읽을 수 있어야 한다.
5. **클릭할 수 있는 버튼에 색 적용.** 사용자가 다음에 눌러야 할 주 버튼에 미리 선택한 메인 컬러와 대비되는 글자색을 적용한다. 보조 버튼은 중립색 윤곽과 동작명으로 구별한다. 정적 KPI 카드에 주 버튼과 같은 채움을 사용하지 않는다.
6. **컴포넌트마다 두 색 이하로 점검.** 각 컴포넌트가 직접 그리는 배경과 전경을 한 쌍으로 제한한다. 아이콘·테두리·포커스 표시는 그 두 색을 재사용하고, 투명 배경은 실제로 비치는 배경색으로 센다. hover·focus·pressed에서도 같은 색 쌍으로 밑줄·윤곽·두께를 바꾼다. 카드 안의 독립 버튼도 자체 색 쌍을 점검한다.

## 메인 컬러 선택

착수할 때 과제 지정 테마, 기존 앱 테마, 키트 프리셋 순으로 선택하고 화면에는 위 4·5단계에서 적용한다. [색상 토큰](assets/theme.css)을 기존 테마에 대응시키거나, 새 웹 앱이라면 앱 스타일 경로에 복사해 한 번 불러온다. 브랜드 지정이 없으면 중립 테마를 쓴다. 하이닉스 또는 크래프톤 테마를 선택했다면 HTML 루트에 각각 `data-hkit-brand="sk-hynix"`, `data-hkit-brand="krafton"`을 설정한다. 주 버튼은 `--hkit-action`과 `--hkit-on-action`을 함께 사용한다.

## 동작 검증과 인계

- 핵심 동작 하나를 입력 → 요청 → 사용자가 확인할 결과까지 연결한다. 빈 결과, 로딩, 오류 후 복구는 해당 흐름에서 구별할 수 있게 한다. 계약 예로 먼저 개발했다면 실제 BE 연결 후 같은 시나리오를 다시 확인한다.
- 화면은 데스크톱 폭(1440px 안팎)에서 확인하고 3단계의 공백 기준을 대조한다. 좁은 폭만 확인하면 넓은 화면에서 벌어진 열과 빈 카드를 놓친다. 캡처가 허용되지 않는 과제에서는 볼 위치를 수동 확인 항목으로 남긴다.
- 허용되는 E2E 테스트 환경에서는 핵심 사용자 입력과 화면의 최종 관찰값을 단언하는 테스트를 작성·실행한다. 자동 실행이 제한된 과제에서는 재현 가능한 수동 E2E 테스트(경로, 입력, 조작, 기대 화면)를 남기고 사용자가 직접 확인한다. 수동 관찰을 전달받기 전에는 UI를 미검증으로 둔다.
- 담당 AC, 변경 경로, 실행한 테스트·결과, 실제 BE/fixture 사용 여부와 남은 수동 확인 항목을 부모에게 돌려준다. HTTP 응답과 화면 검증을 따로 보고한다.
